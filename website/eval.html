การทดลอง: text-only vs image-process

process_image มีผลเฉพาะสเตจ Translation (ส่งรูปหน้าให้ LLM เป็น visual context หรือไม่) การทดลองนี้จึงแปลแต่ละหน้า 2 รอบ แล้วให้ LLM-judge ให้คะแนน ทั้งคู่โดยแนบรูปหน้าเสมอ เพื่อให้ self-bias ของ judge คงที่ทั้งสองฝั่ง → ค่า Δ จึงเทียบกันได้:

# แปล 2 รอบต่อหน้า
text_only  = translate(ocr, image=None)          # ไม่เห็นรูป
image_proc = translate(ocr, image=resized_page)    # เห็นรูปเป็น context
# judge ทั้งคู่ แนบรูปหน้าเสมอ → Δ = image − text_only
⚠️

Self-bias ของ judge: รอบนี้ judge ใช้โมเดลเดียวกับ translator (gemini-3-flash) โมเดลมักให้คะแนนงานตัวเองสูงเกินจริง (เห็นได้จาก ~5/5 รวด) — อ่านคะแนนนี้เป็นสัญญาณ เชิงเปรียบเทียบ เท่านั้น ไม่ใช่คะแนนสัมบูรณ์ (ใช้ --judge-model รุ่นอื่นเพื่อความน่าเชื่อถือ)

ทุก metric สาวกลับไป audit ได้: pairs.jsonl เก็บ 1 แถว/bubble (source → text-only → image → Δ), raw/<id>.json เก็บ system_prompt / raw_response / usage / token ของทุก call — raw มาจาก capture hook ใน code path เดียวกับ production ไม่ใช่ re-implement

เทียบ text-only vs image-process

ผลลัพธ์ของสองโหมดบนหน้าเดียวกัน — ต่างกันที่ คำแปล (โหมด image เห็นรูปประกอบ) ส่วน detection/inpaint เหมือนกัน:

ทั้งสองโหมดอ่านได้ดี ความต่างเชิงคุณภาพเล็กน้อยแต่ไปทางเดียวกัน (image ดีกว่านิดหน่อย) — เห็นชัดในตัวเลขด้านล่าง

📖 อภิธานศัพท์ — รวมความหมายทุกคำ (กดเพื่อกาง)

คำอธิบาย metric อยู่ใต้ชื่อในตารางผลแต่ละหัวข้อแล้ว · ส่วนนี้รวมไว้ที่เดียวเผื่ออ้างอิง รวมถึง คำพื้นฐาน ที่ไม่ได้อยู่ในตาราง ▲/▼ = ทิศที่ดี กลาง ๆ ดูเฉย ๆ

คำพื้นฐาน

reference-free

วัดผล "โดยไม่มีเฉลย" — ไม่ต้องมีคำแปลที่ถูกต้องหรือภาพที่ลบ text ไว้เทียบ ทุก metric คำนวณจาก output ที่ pipeline ผลิตเอง หรือจาก polygon ของฟอง

ground-truth

"เฉลย" ที่คนทำไว้ (เช่น กล่องที่ถูกต้อง / คำแปลมาตรฐาน) — จำเป็นถ้าจะวัดสเตจ 1–2 แบบมาตรฐาน (mAP/CER) จึงยังไม่อยู่ในรอบนี้

LLM-as-judge

ใช้ LLM อีกตัวเป็น "กรรมการ" ให้คะแนนคำแปล — เป็น call แยกหลังแปลเสร็จ เอาคู่ source → translated ไปถาม ไม่ได้แปลใหม่

self-bias

เมื่อ judge เป็นโมเดลเดียวกับ translator มันมักให้คะแนนงานตัวเองสูงเกินจริง → อ่านเป็นค่า เปรียบเทียบ (Δ) เท่านั้น ไม่ใช่คะแนนสัมบูรณ์

bubble · polygon

bubble = ฟองคำพูดหนึ่งใบ (หน่วยที่วัดเกือบทุก metric) · polygon = รูปทรงฟองจริงจาก segmentation ใช้เป็น "ขอบเขต" ในการวัด inpaint/render

Δ (delta) · micro-average

Δ = ค่าโหมด image − โหมด text-only (บวก = image ดีกว่า) · micro-average = เฉลี่ยรวมทุกฟองข้ามทุกหน้า (ฟองเยอะมีน้ำหนักมาก)

สเตจ 3 — Translation

mean_adequacy ▲ สูงดี (1–5)

คำแปล "ตรงความหมาย" ต้นฉบับแค่ไหน — ให้คะแนนโดย LLM-judge

วัดยังไง: เฉลี่ยคะแนน adequacy 1–5 ของทุกฟอง

mean_fluency ▲ สูงดี (1–5)

ภาษาไทยที่ได้ "เป็นธรรมชาติ/ลื่น" แค่ไหน (ไม่ดูความตรงความหมาย ดูแค่ความเป็นธรรมชาติ)

วัดยังไง: เฉลี่ยคะแนน fluency 1–5 จาก LLM-judge

low_adequacy_rate ▼ ต่ำดี

สัดส่วนฟองที่แปล "แย่" (adequacy ≤ 2) — จับ worst case ที่ค่าเฉลี่ยอาจกลบ

วัดยังไง: (จำนวนฟอง adequacy ≤ 2) ÷ ฟองทั้งหมด

fallback_rate ▼ ต่ำดี

สัดส่วนฟองที่ translator "ยอมแพ้" แล้วใช้ข้อความเดิม (API พัง / ไม่มี key / parse ไม่ออก) — ฟองพวกนี้ยังเป็นภาษาต้นฉบับ

วัดยังไง: (ฟองที่ตก fallback) ÷ ฟองทั้งหมด

untranslated_rate ▼ ต่ำดี

สัดส่วน output ที่ "ไม่ใช่ภาษาเป้าหมาย" — โมเดล echo คืนภาษาอังกฤษ หรือปฏิเสธ

วัดยังไง: ตรวจว่า output ไม่มีอักษรไทยเลย ÷ ฟองทั้งหมด

mean_target_script_ratio ▲ สูงดี (0–1)

สัดส่วนตัวอักษรที่เป็น "ภาษาเป้าหมาย" (ไทย) ในผลแปล — ต่ำกว่า 1 มักเพราะมีตัวเลข/SFX/คำอังกฤษปน

วัดยังไง: (จำนวนอักษรไทย) ÷ (อักษรทั้งหมด) เฉลี่ยทุกฟอง

mean_len_ratio ~1 ดี

ความยาวคำแปลเทียบต้นฉบับ — สูงมาก = แปลฟุ่มเฟือย/หลอน, ต่ำมาก = แปลตกหล่น

วัดยังไง: len(คำแปล) ÷ len(ต้นฉบับ) เฉลี่ยทุกฟอง

สเตจ 4 — Inpainting (วัด "ภายใน polygon" หลัง erode ขอบทิ้ง)

interior_std (before / after) ▼ ต่ำดี

ความ "ขรุขระ" ของสีภายในฟอง — ฟองที่ลบ text สะอาดควรเรียบเป็นเนื้อเดียว (std ต่ำ); ยังมี text ค้าง = std สูง

วัดยังไง: ส่วนเบี่ยงเบนมาตรฐาน (std) ของค่า grayscale ของ pixel ในฟอง · ในรายงานคือ 61.8 (ก่อน) → 6.0 (หลัง)

mean_std_reduction ▲ สูงดี (0–1)

ลด std ลงได้กี่ % — ตัวชี้วัดหลักของ inpaint เพราะ ไม่ขึ้นกับสีพื้น (ใช้ได้แม้ฟองพื้นเข้ม)

วัดยังไง: (std_before − std_after) ÷ std_before · 0.903 = ลดได้ 90.3%

mean_ink_removed ▲ สูงดี (0–1)

สัดส่วน "หมึก" (pixel เข้ม = ตัวอักษร) ที่ลบออกได้จริง

วัดยังไง: (หมึกก่อน − หมึกหลัง) ÷ หมึกก่อน · สมมติ text เข้มบนพื้นอ่อน

ink_residual_after ▼ ต่ำดี

หมึก (pixel เข้ม) ที่ "ยังค้าง" หลังลบ — เศษ text ที่ลบไม่หมด

วัดยังไง: สัดส่วน pixel เข้มในฟองหลัง inpaint · 0.009 (จาก 0.112 ก่อนลบ)

สเตจ 5 — Rendering

mean_spill_ratio ▼ ต่ำดี

สัดส่วนตัวอักษรที่แปลแล้ว "ล้นออกนอก" รูปทรงฟอง — อยากให้ text อยู่ในเส้นฟอง

วัดยังไง: diff ภาพ (หลัง render − หลัง inpaint = pixel ตัวอักษร) ที่ตกนอก polygon ÷ pixel ตัวอักษรทั้งหมด

mean_fill_ratio กลาง ๆ

text กินพื้นที่ในฟองไปแค่ไหน — สูงไป = อัดแน่นอ่านยาก, ต่ำไป = ตัวเล็กเกิน เหลือที่ว่างเยอะ

วัดยังไง: (pixel ตัวอักษร) ÷ (พื้นที่ polygon ของฟอง)

truncated_rate ▼ ต่ำดี

สัดส่วนฟองที่ข้อความ "ยาวเกินจนถูกตัดด้วย …" แม้ย่อฟอนต์จนเล็กสุดแล้ว (ที่จริงใส่ไม่หมด)

วัดยังไง: เรียก fit logic จริงของ renderer ซ้ำต่อฟอง แล้วนับฟองที่ต้อง truncate

mean_font_size · mean_lines ดูเฉย ๆ

ขนาดฟอนต์ / จำนวนบรรทัดเฉลี่ยต่อฟอง — ไม่มีทิศ "ดี/แย่" ตายตัว ใช้ดูว่าโหมดต่าง ๆ เรนเดอร์ต่างกันแค่ไหน

ต้นทุน

translate_tokens_per_page ▼ ต่ำ = ถูก

token เฉลี่ยที่ใช้แปล 1 หน้า — โหมด image-process แพงกว่าเพราะส่งรูปเป็น context (999 → 2,103)

translate_cost · judge_cost USD

ค่า API รวมทั้ง dataset — แยกค่าแปล (translate) กับค่ากรรมการ (judge) ออกจากกัน

ข้อจำกัดของการวัดรอบนี้

  • self-bias: judge = translator รุ่นเดียวกัน → คะแนน adequacy/fluency สูงเกินจริง อ่านเป็น Δ เชิงเทียบเท่านั้น
  • dataset เดียว: Grand Blue ch.29 แหล่งเดียว 31 หน้า — ยังไม่ครอบสไตล์/สำนักพิมพ์อื่น
  • ไม่วัดสเตจ 1–2: Detection/OCR ต้องมี ground-truth (mAP/CER) ถึงวัดได้ — งานถัดไป
  • SFX: reference-free จับไม่ได้ตรง ๆ ว่า SFX ไม่ถูกแปล (เห็นทางอ้อมผ่าน target_script_ratio < 1)
